<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|--------------|
| Browser (participant input) → `PATCH`/`POST`/`DELETE /trips/:tripId/items[/:itemId]` | Untrusted field values (Name, Category, PackedBy selection, etc.) cross into Phase 7's write endpoints |
| Shared table → all trip participants | Any participant's write is visible to every other participant on next fetch (no per-user isolation within a trip) |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|------------------|
| T-08-04 | Tampering | Optimistic UI rollback (`handleFieldChange`) | medium | mitigate | Rollback restores the last known-good SERVER value from the previous response (not merely "undo the keystroke"), so a user is never shown a value that was never actually persisted (RESEARCH Security Domain) |
| T-08-05 | Spoofing | PackedBy field (client-supplied identity) | medium | mitigate | PackedBy is edited via a `<select>` constrained to `trip.participants` (D-05) — never free text — and the server independently re-validates against the real participant list regardless of client input (Phase 7 D-04) |
| T-08-06 | Denial of Service (self, data-integrity) | "+ Add item" rapid double-click | low | mitigate | The Add-item button disables itself while its own `POST` is in flight, preventing runaway duplicate blank-row creation in a table every participant sees |
| T-08-07 | Tampering (of displayed state) | 409 conflict handling | medium | mitigate | 409 gets a dedicated branch — roll back, show the verbatim server message, offer only a manual "Refresh" (full re-fetch) — never a blind auto-retry loop (RESEARCH Pitfall 3) |

</threat_model>
